# Fase 11 — VS Code y LSP

**Estado:** en curso. La extensión asocia `.ox`; el LSP comparte lexer/parser, entrega semantic tokens, hover, completado, símbolos, definición y referencias locales, y calcula diagnósticos de edición en un worker separado. El índice local de declaraciones cubre funciones, métodos, estructuras, enumeraciones, rasgos, alias de tipo y módulos; resuelve cualificadores como `dominio::modelos::Alumno::nuevo`, distingue nombres repetidos en módulos distintos y devuelve todas las ubicaciones candidatas cuando no puede desambiguar. Los resultados viejos se cancelan y descartan al cambiar o cerrar el documento. El servidor limita 64 documentos, 4 MiB por documento, 16 MiB de texto abierto, cuatro cálculos concurrentes de semantic tokens, una comprobación Cargo y una tarea de diagnóstico en cola. `oxido/check` se ejecuta en un worker: el bucle sigue respondiendo `oxido/stats` y otras solicitudes, y `$/cancelRequest` marca la solicitud y mata el árbol de procesos de Cargo; una prueba host lo verifica con un Cargo controlado que tarda y deja marcadores de inicio y fin. El editor dispone de `Óxido: Ver estadísticas del editor`, que muestra documentos, bytes, rondas de diagnóstico, duración del último diagnóstico, memoria residente en Linux y tiempo de ida y vuelta; en Windows y macOS la memoria se informa como no disponible, sin inventar una métrica. En un workspace confiable, un worker persistente consulta `rust-analyzer` sobre un árbol Rust temporal resuelto desde los módulos `.ox`; las ubicaciones devueltas para archivos mapeados vuelven al URI y rango del `.ox` de origen. Sus solicitudes y las del propio analizador se acotan para no bloquear el bucle LSP. `textDocument/formatting` de modo indentado usa el mismo formateador que `oxido formato`, extraído a `oxido-compiler`; la prueba host exige el texto canónico exacto. `Óxido: Comprobar con Cargo` se ejecuta en un Extension Development Host real: usa el `oxido.toml` validado, el `Cargo.lock` del proyecto y una dependencia de crates.io vendorizada, y devuelve el `E0308` de rustc al archivo `.ox` del módulo donde está el error. Una ejecución host en Restricted Mode comprueba que ni la extensión ni el servidor invocan Cargo. El VSIX 0.1.0 se empaqueta con `npm run package:vsix` y se instala con la CLI de VS Code en un perfil limpio; un caso host adicional exige que la extensión activa proceda del directorio de extensiones instaladas, que el paquete no contenga pruebas ni perfiles, y que un `.ox` reciba `OX1002` desde `oxido-lsp`. No se cierra la fase: falta ampliar la evidencia semántica entre módulos, publicar/distribuir el VSIX y resolver el binario LSP por plataforma, porque el VSIX no incluye `oxido-lsp`; las métricas de memoria fuera de Linux quedan explícitamente no disponibles en este corte.

La decisión de seguridad está en [ADR 0010](adr/0010-frontera-lsp-y-confianza-editor.md). El servidor LSP no inicia Cargo ni `rust-analyzer` al abrir o editar; `Óxido: Comprobar con Cargo` es una acción separada que exige confianza y usa el `oxido.toml` validado del proyecto. Leer `oxido.toml` no ejecuta código. La extensión declara soporte `limited` para Workspace Trust y restringe la configuración `oxido.serverPath` en Restricted Mode.

## Evidencia host de Cargo

- `editors/vscode-oxido/test/fixtures/cargo/` declara `itoa` 1.0 y fija `Cargo.lock`. La prueba configura un `CARGO_HOME` temporal cuyo `config.toml` apunta al vendor versionado `tests/fixtures/cargo-registry/vendor`; no usa la caché del desarrollador ni la red.
- `check_error.ox` importa `util_error.ox`, que contiene `dejar numero: i32 = "texto"`. El comando `Óxido: Comprobar con Cargo` devuelve `success: false`, `dependencyCount: 1`, `lockfilePresent: true`, y un `E0308` en `util_error.ox` línea 3 (0-based), carácter 24, con rango final 31.
- La misma prueba calcula el SHA-256 de `Cargo.lock` antes y después y exige que no cambie. Si el vendor no existe, el runner falla con un mensaje explícito; no declara el caso aprobado.
- El caso Restricted Mode usa un perfil nuevo de VS Code, un `cargo` falso en `PATH` que escribiría un marcador, y comprueba que el marcador no aparece tras ejecutar el comando y una solicitud `oxido/check` directa.

## Evidencia host de cancelación Cargo

- `Óxido: Comprobar con Cargo` deja de ejecutarse dentro del bucle de `serve_stdio`. El servidor valida la confianza y el documento, toma una instantánea, y lanza `run_cargo_check` en un hilo `oxido-lsp-cargo-check`. La respuesta vuelve como evento al bucle, que la descarta si la solicitud fue cancelada o si el documento cambió.
- `oxido-cargo::run_with_timeout_cancellable` consulta una bandera atómica cada 20 ms y, al activarse, mata el grupo de procesos de Cargo; las funciones del compilador comprueban la bandera antes de lanzar cada paso y no inician comandos posteriores.
- El caso host `cancellation` ejecuta un workspace confiable con `OXIDO_CARGO_BINARY` apuntando a un Cargo controlado que escribe un marcador de inicio, duerme 30 s y escribiría un marcador de fin al terminar. El runner espera el marcador de inicio, exige que `oxido/stats` responda en menos de 1,5 s, cancela con un `CancellationToken` real y comprueba que la promesa termina con `-32800` y que el marcador de fin no existe. `OXIDO_CARGO_BINARY` es una anulación explícita del entorno del operador; el workspace no puede configurarla.
- `cargo test -p oxido-cargo --offline` cubre la cancelación previa al lanzamiento y `cargo test -p oxido-lsp --offline` cubre que `$/cancelRequest` marca tanto semantic tokens como una comprobación Cargo pendiente.

## Evidencia host de navegación y formato

- `editors/vscode-oxido/test/fixtures/navigation/` contiene `alpha.ox` y `beta.ox`, ambos con una función `repetida`, y `dominio/modelos.ox` con la estructura `Alumno` y el método asociado `nuevo`.
- El caso host se ejecuta en Restricted Mode, sin `--disable-workspace-trust`. Abre `main.ox` y solicita definición en `alpha::repetida`, `beta::repetida`, `dominio::modelos::Alumno` y `dominio::modelos::Alumno::nuevo`; exige que cada consulta vuelva al archivo correcto. También comprueba que el hover de `nuevo` identifica un método y que las referencias de `alpha::repetida` no incluyen `beta.ox`.
- El mismo caso abre `messy.ox`, con espaciado y sangría no canónicos, y solicita `textDocument/formatting`. Exige exactamente `sintaxis indentacion\nfuncion suma(a: i32, b: i32) -> i32:\n    retornar a + b\n`, producido por el formateador compartido con `oxido formato`.
- `cargo test -p oxido-lsp --offline` añade pruebas unitarias para nombres repetidos, tipos/métodos anidados, referencias cualificadas y símbolos de documento; `cargo test -p oxido-compiler --offline` y `cargo test -p oxido-cli --offline` conservan la conformance de la CLI.

## Evidencia de empaquetado e instalación VSIX

- `npm run package:vsix` ejecuta `vsce package` con `@vscode/vsce` 3.9.2 fijado como dependencia de desarrollo y escribe `dist/oxido-language-support-0.1.0.vsix`. `.vscodeignore` excluye `test/`, `.vscode-test/`, `dist/` y `package-lock.json`; el paquete conserva `src/`, el manifiesto, la configuración de lenguaje, el README y las dependencias de producción de `vscode-languageclient`.
- El VSIX no incluye el binario `oxido-lsp` ni un proceso auxiliar dependiente de plataforma. La instalación usa `oxido-lsp` desde `PATH` o `oxido.serverPath`, igual que el host de desarrollo. No está firmado ni se ha publicado en un marketplace.
- `npm run test:vsix` empaqueta, crea un perfil limpio, instala con la CLI de VS Code 1.143.1 y lanza el host con un arnés mínimo como extensión de desarrollo. La extensión de Óxido debe descubrirse desde el directorio de extensiones instaladas, no desde el árbol del repositorio. La prueba compara la ruta real con la instalada, exige la versión `0.1.0`, comprueba que no se empaquetaron pruebas/perfiles/lockfile/dist, abre `main.ox` y exige `languageId = oxido` y un `OX1002` publicado por `oxido-lsp`.
- `@vscode/vsce` es una dependencia de desarrollo y no se incluye en el VSIX. `npm audit` no reporta hallazgos con los `overrides` fijados en `package.json`; esos overrides solo afectan al árbol de empaquetado, no al código de la extensión.

El job `vscode-extension` de CI compila `oxido-lsp`, ejecuta la suite de manifiesto y lanza VS Code 1.143.1 con un workspace confiable. Abre un `.ox`, recibe el diagnóstico `OX1002` real y solicita hover, estadísticas, completado, inlay hints y definición a través del cliente LSP real; además verifica que `util::saludo()` navega a `util.ox`. La prueba exige al menos una respuesta real de `rust-analyzer`, no solo el fallback local. El caso Cargo ejecuta una compilación real, el caso de navegación/formato demuestra el índice local y el formateador compartido sin confianza, el caso de cancelación demuestra que el bucle responde durante Cargo y mata el proceso, el caso VSIX empaqueta, instala y activa la extensión desde un perfil limpio, y el caso restringido demuestra que no se inicia Cargo. `OXIDO_HOST_ONLY=cargo` permite repetir un caso durante el desarrollo; también se aceptan `navigation`, `cancellation`, `installed` y `restricted`.

La suite host sí ejecuta VS Code, el bridge disponible de `rust-analyzer` y Cargo; las pruebas de protocolo y manifiesto no sustituyen pruebas de Cargo, mapeo semántico completo ni otras funciones pendientes del editor. La compilación Cargo del host usa una dependencia vendorizada concreta; no demuestra descarga desde crates.io ni compatibilidad general de dependencias.

## Instalación de desarrollo

1. Compila el servidor: `cargo build --release -p oxido-lsp`.
2. Asegúrate de que `oxido-lsp` esté en `PATH` o configura `oxido.serverPath` en ajustes de usuario.
3. Abre `editors/vscode-oxido` como proyecto de extensión con Extension Development Host, o empaqueta e instala el VSIX local:

   ```sh
   npm --prefix editors/vscode-oxido run package:vsix
   code --install-extension editors/vscode-oxido/dist/oxido-language-support-0.1.0.vsix
   ```

   El VSIX no incluye `oxido-lsp`; el paso 2 sigue siendo necesario. El paquete local no está firmado ni se distribuye desde un marketplace.
4. Abre un proyecto `.ox` con `oxido.toml` válido o un archivo con cabecera `sintaxis indentacion`/`sintaxis llaves`.

La configuración leída desde el workspace solo selecciona el modo y está limitada por el parser de configuración; no contiene comandos. El análisis al editar es local. El comando Cargo requiere confianza explícita y usa `--locked --offline`; no habilita dependencias de usuario desde el LSP en este corte.
