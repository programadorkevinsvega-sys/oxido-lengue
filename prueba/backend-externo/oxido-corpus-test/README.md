# XOVYRA Backend

El backend se implementa como workspace Rust modular. El alcance y secuencia de producto están en [`roadmap.md`](roadmap.md); las restricciones arquitectónicas están en [`reglas-estrictas-de-arquitectura-monolito-modular-rust-universal.md`](reglas-estrictas-de-arquitectura-monolito-modular-rust-universal.md); la evidencia de infraestructura está en [`docs/fase-2-infraestructura-y-base-de-datos.md`](docs/fase-2-infraestructura-y-base-de-datos.md) y el estado de identidad en [`docs/fase-3-seguridad-y-usuarios.md`](docs/fase-3-seguridad-y-usuarios.md).

## Preparar el entorno de desarrollo

Requisitos: Rust `1.99.1` con `rustfmt` y `clippy`, Docker Engine con Compose, y acceso al registry de crates. El repositorio fija PostgreSQL, Redis y NATS en `compose.yaml`; las imágenes se referencian por digest. Compose publica puertos solo en loopback.

1. Crea y mantén `backend/.env` directamente, usando `.env.example` como referencia de nombres y agregando las credenciales de los servicios que ya tienes levantados (`NATS_URL`, `NATS_USERNAME`, `NATS_PASSWORD`, `REDIS_URL` y URLs de PostgreSQL). Los ejecutables de migraciones, runtime y BFF cargan ese archivo mediante `dotenvy`; no hace falta un generador de `.env`. Configura allí los orígenes exactos del frontend, `BFF_SECURE_COOKIES=false` solo para orígenes loopback HTTP locales y los tiempos de vida de sesión. No incrustes contraseñas en URLs. El archivo nunca se versiona y tiene permisos solo para el usuario. En producción, usa orígenes HTTPS, cookies Secure y el gestor de secretos del despliegue. Las variables de Resend también se configuran en este archivo local; no guardes credenciales en Git.
2. Arranca los servicios reales con `docker compose --env-file .env up --detach --wait` cuando quieras usar el Compose local. Si ya ejecutas esos servicios por separado, configura sus endpoints y credenciales en `.env` y no levantes otro Compose.
3. Los binarios cargan `backend/.env` automáticamente cuando existe; las variables ya presentes en el proceso conservan prioridad. En un volumen PostgreSQL vacío, Compose inicializa la base y los roles de contexto configurados. Para un volumen ya inicializado o para alinear roles con `.env`, ejecuta `sh scripts/bootstrap-existing-postgres.sh`; no crea ni arranca contenedores y localiza PostgreSQL mediante el servicio Compose activo, no por un nombre fijo de contenedor. Después ejecuta `cargo run -p xovyra-migrator`: usa `MIGRATOR_DATABASE_URL`, asume un rol propietario a la vez y aplica las migraciones de todos los contextos a sus schemas. Compose crea la base física; el migrador crea schemas y tablas. Runtime usa URLs separadas por módulo con roles de privilegios mínimos. Para una intervención operativa acotada, `cargo run -p xovyra-migrator -- --context platform_control` aplica solo las migraciones de ese bounded context; úsalo únicamente cuando un bloqueo ajeno requiera aislar un contexto, nunca como sustituto de la ejecución global normal.
4. Para transferencias reales configura el conjunto completo `CLOUDFLARE_R2_ENDPOINT`, `CLOUDFLARE_R2_BUCKET`, `CLOUDFLARE_R2_ACCESS_KEY_ID` y `CLOUDFLARE_R2_SECRET_ACCESS_KEY` en `.env`; el token R2 S3 debe tener permiso `Object Read & Write` aplicado al bucket configurado; revisa también que endpoint incluya el ID de cuenta correcto y que el bucket sea el mismo al que se limitó el token. `XOVYRA_SCRATCH_ROOT`, `XOVYRA_SCRATCH_RETENTION_SECONDS` y `ASSET_WORKER_AUTH_SECRET` controlan temporales y autenticación interna del worker. No copies secretos a `.env.example`. El navegador obtiene URLs presignadas de corta duración a través del BFF y manda los bytes directamente a R2; el BFF/runtime nunca proxyan el contenido. En Cloudflare Dashboard → R2 → bucket `xovyra-ai` → Settings → CORS Policy, agrega orígenes exactos `https://app-xovyra.jnmtortas.com` y `https://admin-xovyra.jnmtortas.com`, métodos `PUT`, `GET`, `HEAD`, header `Content-Type`, y expone `ETag`. Para desarrollo incluye `http://localhost:5173`, `http://127.0.0.1:5173`, `http://localhost:5174` y `http://127.0.0.1:5174`; no agregues el host de API como origen. Ejemplo para la pestaña JSON:

   ```json
   [{
     "AllowedOrigins": [
       "https://app-xovyra.jnmtortas.com",
       "https://admin-xovyra.jnmtortas.com",
       "http://localhost:5173",
       "http://127.0.0.1:5173",
       "http://localhost:5174",
       "http://127.0.0.1:5174"
     ],
     "AllowedMethods": ["PUT", "GET", "HEAD"],
     "AllowedHeaders": ["Content-Type", "Range"],
     "ExposeHeaders": ["ETag"],
     "MaxAgeSeconds": 3600
   }]
   ```

   Agrega los orígenes locales solo para desarrollo y no uses `*`. Cloudflare exige CORS para URLs presignadas usadas desde navegador; el origen debe coincidir exactamente y el `Content-Type` enviado debe coincidir con el firmado ([CORS de R2](https://developers.cloudflare.com/r2/buckets/cors/), [URLs presignadas](https://developers.cloudflare.com/r2/api/s3/presigned-urls/), [credenciales S3 y permisos R2](https://developers.cloudflare.com/r2/api/tokens/)).
5. Inicia el runtime gRPC con `cargo run -p xovyra-module-runtime` y el BFF REST con `cargo run -p xovyra-bff`.
6. El BFF publica OpenAPI en `http://127.0.0.1:8080/openapi.json`, liveness en `/health/live` y readiness en `/api/v1/system/health`. Readiness consulta por gRPC el estado real de PostgreSQL, Redis y NATS. Redis es caché auxiliar autenticada; ningún dato crítico depende solo de ella. El navegador no se conecta a gRPC.
7. El acceso global de plataforma no se asigna por registro ni por migración. Tras verificar una cuenta por el flujo real de identidad, un operador con acceso controlado al entorno puede conceder o revocar un rol mediante `cargo run -p xovyra-platform-operator-provisioner -- grant --email DIRECCION --role platform_admin --reason 'motivo auditado'` o la acción `revoke`. La herramienta usa `IDENTITY_DATABASE_URL` de `.env`, exige una razón y registra el resultado; nunca imprime contraseñas ni secretos. No ejecutes el aprovisionamiento hasta decidir qué cuenta real recibirá acceso.

## Dominios públicos y CORS

La API pública se sirve en `https://api-xovyra.jnmtortas.com`. El navegador se origina en las aplicaciones, no en el host de la API: tenant usa `https://app-xovyra.jnmtortas.com` y administración usa `https://admin-xovyra.jnmtortas.com`. En desarrollo local tenant corre en `http://localhost:5173` y administración en `http://localhost:5174` (también se permiten sus equivalentes `127.0.0.1`). Configura listas exactas y separadas en `BFF_TENANT_ALLOWED_ORIGINS` y `BFF_PLATFORM_ALLOWED_ORIGINS`; el BFF las aplica respectivamente a `/api/v1/*` y `/platform/*`. Todos los endpoints tenant, incluidos archivos y trabajos, usan el prefijo versionado `/api/v1`; las rutas sin prefijo no forman parte del contrato ni reciben CORS tenant. No agregues rutas, comodines ni el origen de la API. El webhook Resend es server-to-server y no recibe CORS de navegador. En producción, `BFF_SECURE_COOKIES=true` y `PUBLIC_APP_ORIGIN=https://app-xovyra.jnmtortas.com`. Los dos frontends usan `VITE_API_BASE_URL=https://api-xovyra.jnmtortas.com`; esa variable solo contiene la URL pública de la API y no es un secreto. CORS no reemplaza autenticación ni permisos.

Cada petición HTTP registra eventos correlacionados de inicio y final. El evento final incluye `event`, `service`, `component`, `operation`, `http.method`, ruta segura sin query/valores, `http.status_code`, `duration_ms`, `correlation_id` y `trace_id`. Un 5xx agrega `error.code`, `error.category`, mensaje técnico saneado, `retryable` confirmado y dependencia/resultado si se conocen; no se acepta el status HTTP como explicación única. Cada llamada gRPC registra inicio, resultado, código y duración en ambos lados de la frontera; el runtime abre un span servidor que extrae `traceparent` y `x-correlation-id`, por lo que los errores internos heredan ambos identificadores. Las etapas de base de datos, Redis, JetStream y proveedores registran su propia dependencia/operación/duración y metadatos técnicos seguros disponibles. No se registran cookies, tokens, cuerpos, cabeceras sensibles, parámetros de búsqueda ni mensajes crudos de proveedores. `X-Correlation-ID` y `traceparent` se propagan por HTTP, gRPC y eventos.

### Errores estructurados en todo el sistema

Esta política rige todos los dominios, módulos, workers, BFF, integraciones y frontends, desde la primera fase. Todo fallo produce un evento estructurado con `event`, servicio/componente, operación, clase y código estable, dependencia afectada, resultado, duración y `correlation_id`/`trace_id`; incorpora metadatos técnicos seguros como SQLSTATE, código gRPC/HTTP/proveedor, constraint, tabla, reintento y tiempo de espera cuando existan. Un status 4xx/5xx o un `error_type` sin causa segura no satisface el requisito. Registra las etapas relacionadas (entrada, llamada a dependencia, causa clasificada, traducción HTTP y resultado final) con los mismos identificadores. Distingue validación, autorización, conflicto, timeout, conectividad/pool, persistencia, serialización y fallo externo. La respuesta al usuario lleva código estable, explicación clara, detalles seguros y referencia de solicitud, con recuperación o espera cuando corresponda. Nunca se registran ni muestran secretos, credenciales, cookies, tokens, URLs firmadas, contenido privado, datos sensibles, SQL crudo ni stack traces. Toda fase y subfase documenta, implementa y prueba el recorrido de error del módulo dueño a gRPC, BFF REST y UI, incluida propagación y redacción.

La prueba automatizada de cada fase debe emparejar cada cierre HTTP fallido con el evento causal de la operación por `correlation_id` **y** `trace_id`, y comprobar que preserva su código/categoría específica. Un test del status HTTP sin ese evento causal no demuestra diagnóstico suficiente. Añade pruebas unitarias de clasificación y pruebas de integración sobre las fronteras reales aplicables; no dejes como aceptación ordinaria del backend/BFF una secuencia que solo pueda comprobarse manualmente en navegador.

PostgreSQL ejecuta `infra/postgres/001-context-roles.sh` únicamente al inicializar un volumen vacío. Compose debe pasar explícitamente las credenciales de los roles `platform_control`, `notifications` y `realtime` que consume el inicializador. Si ese primer arranque falla, corrige la causa y usa el bootstrap idempotente para completar roles en la base ya inicializada; no borres volúmenes persistentes como mecanismo automático de recuperación. El inicializador crea roles NOLOGIN dueños de schema/migraciones y roles de runtime separados, sin acceso a schemas ajenos.

## Verificación de infraestructura

Instala Buf CLI `1.50.0` desde la [documentación oficial](https://buf.build/docs/cli/installation/) para validar contratos protobuf. Ejecuta `sh ./scripts/verify-proto-contract.sh` para compilar `platform/proto` y comprobar compatibilidad de fuente/wire con las reglas `FILE` contra el contrato de la rama local `main`. El verificador integral también ejecuta este gate.

`sh ./scripts/verify-phase-2.sh` usa únicamente los contenedores existentes configurados en `.env`; no inicia, detiene ni elimina contenedores/volúmenes. Inicializa roles PostgreSQL, crea y elimina una base aleatoria temporal para verificar instalación vacía/repetible y aislamiento, y luego comprueba la base configurada, Redis autenticado, JetStream, Outbox, REST/OpenAPI, trace context, señales de apagado y degradación de readiness. Las pruebas de Outbox limpian su fila y subject aleatorios; la verificación elimina solo recursos temporales propios.

No uses `docker compose down --volumes` sobre un entorno persistente. Para desarrollar con datos reales locales, conserva el proyecto Compose y sus volúmenes hasta que decidas explícitamente eliminarlos.

## Fase 4.4: archivos y trabajos tenant

Biblioteca y Trabajos llaman exclusivamente a `/api/v1/assets...` y `/api/v1/jobs...`. El prefijo es necesario para el enrutamiento, la política CORS tenant y la versión contractual; no se debe construir una URL tenant sin `/api/v1`.

Las pruebas PostgreSQL reales de los dominios se ejecutan con `cargo test -p xovyra-asset-storage --test assets_real` y `cargo test -p xovyra-jobs --test jobs_real`. El consumidor durable de invitaciones se verifica mediante la prueba indicada en `docs/fase-4-multi-tenancy-y-equipos.md`. La recuperación realtime tras reiniciar Redis se verifica con `cargo test -p xovyra-module-runtime realtime_service::tests::realtime_redis_subscription_and_cache_reconnect_after_dev_redis_restart -- --exact --test-threads=1`; Redis y JetStream durables se comprueban con `cargo test -p xovyra-platform --test dependency_restart_real -- --exact redis_and_jetstream_clients_recover_after_restarting_configured_dev_services --test-threads=1`. **Estas pruebas reinician los contenedores ya existentes indicados por `REDIS_CONTAINER` y `NATS_CONTAINER` en `backend/.env`; ejecútalas solo contra el entorno de desarrollo y cuando la interrupción breve de esos servicios sea aceptable. No crean contenedores nuevos.** La prueba Cloudflare R2 `cargo test -p xovyra-module-runtime --features real-r2-tests r2_storage::real_integration::direct_presigned_upload_head_download_and_delete_use_real_cloudflare_r2 -- --exact` contacta el bucket configurado y crea/limpia un objeto transitorio; ejecútala únicamente con credenciales y permisos R2 de prueba. La fase no se considera cerrada mientras falle esa prueba R2 o estén pendientes los demás gates multi-réplica descritos en el documento de fase. La entrega positiva de invitación con Resend real se valida con `cargo test -p xovyra-module-runtime --features real-resend-tests tenancy_invitation_worker::tests::invitation_worker_delivers_email_through_real_resend_and_persists_success -- --exact --test-threads=1`, configurando `RESEND_TEST_RECIPIENT` con un buzón controlado. Envía un correo real y verifica el estado en PostgreSQL; requiere una API key válida y nunca debe ejecutarse con credenciales expuestas.

## Aceptación automatizada Fase 4.5

Desde `backend/`, `bash scripts/verify-phase-4.5.sh` ejecuta formato, Clippy, build BFF/runtime, pruebas unitarias del BFF, integraciones de journal, migración limpia y aislamiento de roles en una base temporal del PostgreSQL de desarrollo existente, y el recorrido real HTTP→BFF→gRPC con PostgreSQL/Redis/JetStream. También ejecuta Vitest, lint y build de `frontend/admin_plataform`. Los verificadores localizan el contenedor mediante `docker compose ps -q postgres`; no dependen del nombre generado por Compose. La prueba integrada crea y limpia sus propios datos, inicia BFF/runtime en puertos temporales y no toca los procesos que el usuario haya iniciado manualmente. Además inicia un BFF de diagnóstico apuntado a un puerto gRPC cerrado para comprobar de forma determinista el 503 de readiness. El script verifica que cada cierre HTTP fallido tenga un evento causal con los mismos `correlation_id` y `trace_id`, y conserve el código específico. La revalidación del 2026-10-27 pasó los 9 tests BFF, 3 integraciones journal, 3 pruebas de migración/grants y aislamiento, el flujo HTTP→BFF→gRPC y los gates Vitest/lint/build admin; 7 cierres HTTP fallidos se emparejaron con sus causas operativas.

La comprobación contra Cloudflare R2 real crea y elimina un objeto temporal: `PHASE45_VERIFY_R2=1 bash scripts/verify-phase-4.5.sh`. Ejecútala solo con el bucket de desarrollo configurado en `.env` y cuando sea aceptable escribir ese objeto. Las verificaciones usan el stack existente y no crean contenedores.

La revalidación más reciente del entorno y su resultado están en [`docs/auditoria-estado-2026-10-27.md`](docs/auditoria-estado-2026-10-27.md). La aceptación automatizada de Fase 4.5 se repitió con PostgreSQL, Redis y JetStream del Compose de desarrollo el 2026-10-27; la evidencia de R2 y Resend real corresponde a ejecuciones separadas documentadas antes de esa fecha.

## Arquitectura realtime transversal

Toda fase/subfase que cambie datos persistidos visibles integra Outbox del módulo dueño, publicación duradera en JetStream, señal WebSocket a través del BFF/gateway modular y recuperación REST. El gateway es un módulo del mismo monolito, con contrato gRPC, no un microservicio separado. Tenant y administración consumen coordinadores TanStack Query globales pero aislados por build, sesión y audiencia. El socket invalida/refresca queries; REST y PostgreSQL conservan la autoridad.

El relay publica envelopes versionados con `event_id`, `event_type`, `event_version`, `occurred_at`, `correlation_id` y `payload`. La correlación se toma del payload transaccional; para eventos legados que no la tengan, se usa el ID durable del evento. Los consumidores deben validar audiencia/scope, persistir efectos idempotentes y diferenciar errores transitorios de eventos inválidos permanentes para evitar ciclos de reintento sin fin.

El diseño admite varias réplicas de BFF, runtime/gateway, frontend, NATS/JetStream, Redis y PostgreSQL. JetStream/Outbox recupera eventos durables; Redis HA Pub/Sub solo distribuye señales efímeras entre réplicas y puede fallar sin pérdida de datos. PostgreSQL primario recibe escrituras y sus réplicas solo sirven lecturas con control de lag/read-your-writes. Reconexion WebSocket usa cursor y REST delta/snapshot para deduplicar, corregir huecos o desorden; se conserva sincronización manual. La instancia local única de Redis sirve al desarrollo actual y no debe convertirse en supuesto arquitectónico de producción.
